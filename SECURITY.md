# Security Policy

Org-wide default for every repository under [AxiNine](https://github.com/AxiNine). A repository may add
its own `SECURITY.md` to override this one.

> ⚠️ **Before this goes public, replace the contact address below.** It is a placeholder. A security policy
> that routes reports to an address nobody reads is worse than having no policy, because it converts a
> researcher who would have chased you into one who assumes you were told.

## Reporting a vulnerability

Email **security@axinine.example** — *placeholder, see the warning above*. Do not open a public issue.

Please include: the repository, what you did, what happened, and what you expected. A proof of concept
helps but is not required to report.

We will acknowledge within **3 working days** (Asia/Bangkok) and give an assessment within **10 working
days**. If we disagree that something is a vulnerability we will say so and explain why, rather than
letting the thread go quiet.

## What this platform holds

AxiNine is multi-tenant SaaS for Thai schools and local government. The data includes minors' records and
personal data under **PDPA**. Two classes of finding are treated as critical regardless of how hard they
are to trigger:

- **Cross-tenant access** — anything that lets one tenant read, infer or modify another's data. Isolation
  is enforced in two layers (application query filter and PostgreSQL row-level security); a bypass of
  either is a critical finding even when the other still holds, because the second layer is what covers
  the bug in the first.
- **Authentication and session handling** — password verification, MFA enforcement, token issuance and
  revocation. One token is scoped to exactly one tenant by design; anything that widens that is critical.

## Scope

In scope: all code under the AxiNine organisation, and the deployed application.

Out of scope: findings against third-party services we merely use; reports generated by a scanner with no
evidence the issue is reachable in this application; and denial of service through sheer volume.

## What we run against ourselves

Every repository runs, on pull requests and nightly (see [`docs` §8.5][doc]):

- secret scanning over full git history (gitleaks)
- a blocking dependency advisory gate — the NuGet audit as a build error in the backend, `npm audit` at
  high severity in the JavaScript repos
- lock files enforced on restore, so a build cannot resolve a different dependency graph than the one
  reviewed
- container images pinned by digest
- an SBOM and a build-provenance attestation for each shipped artefact

This list is what is actually wired, not what is planned. Where a control is missing it is written down as
missing in §8.5 rather than omitted from this page.
